## Finding 1 — HIGH: Start.bat tells the operator the wrong URL whenever the panel falls back to a different port

**WHERE:** `build.js:259-260` (generates Start.bat's banner) vs. `server/index.js:2734-2748`
(the panel's own, correct, dynamic port log).

**WHAT HAPPENS:** Start.bat prints this unconditionally, before it even launches the panel:
```
echo Starting Zomboid Control Panel...
echo Open your browser to: http://localhost:3001
```
That `3001` is a hardcoded literal, not read from anywhere. Separately, the panel itself
already has correct, working fallback logic for when 3001 is unavailable
(`server/index.js:2734-2748`): it retries with `listenPort=0` (OS-assigned free port),
persists the result via `setSetting("panelPort", boundPort)`, and logs the truth a few
lines later: `Configured panel port 3001 was unavailable; switched to free port <X> and
saved it` followed by `Local: http://localhost:<X>`.

**HOW I KNOW — reproduced for real, not just read the code:** I had two of my own test
instances collide on 3001 (my own test-hygiene mistake, not a bug — I left an earlier
instance running). The second instance's console showed exactly this sequence:
```
Open your browser to: http://localhost:3001        <- Start.bat, wrong, first thing shown
...
[panel boots]
Configured panel port 3001 was unavailable; switched to free port 62673 and saved it
Local: http://localhost:62673                        <- correct, several lines later
```
Confirmed via `Invoke-WebRequest http://localhost:62673/` (200, real setup-wizard HTML)
that 62673 was in fact the live one, while 3001 had nothing listening.

**WHY THIS MATTERS BEYOND THE ONE-OFF:** the fallback port gets *saved*
(`panelPort` setting), so once it fires once, it can keep firing on every subsequent
launch too — Start.bat's banner never gets more correct, it's just wrong on a
per-installation basis instead of a one-time fluke. A non-technical operator whose first
launch happens to collide with anything already on 3001 (another instance, another app,
a leftover TIME_WAIT) is told an address that will just fail to load, with the correct one
buried in scrolling text they have no reason to read since they were just told where to go.

**WHAT SHOULD HAPPEN:** either Start.bat shouldn't print a URL at all (let the panel's own
`Local: http://localhost:<port>` line be the one and only instruction), or the two need to
actually agree — Start.bat can't know the real port in advance since it's the panel's own
runtime fallback, so the honest fix is dropping the batch file's own guess.

**SEVERITY: High.** This is exactly the "says something false about itself" class flagged
as highest-value tonight, and it's the very first line of guidance a brand-new operator
sees.

## Finding 2 — HIGH: double-clicking the exe a second time (same install, already running) doesn't refuse cleanly — it crash-loops

**WHERE:** the exe→Start.bat handoff (`server/index.js:75-109`) and Start.bat's own binary
resolution (`build.js:270-271`).

**WHAT GOD ASKED:** "If they double-click it a SECOND time while it is already running,
what happens? We fixed a lock that refuses a second instance — does the refusal explain
itself, or does a window flash and vanish leaving them convinced it is broken?"

**WHAT ACTUALLY HAPPENS:** neither. `pidLock.js`'s refusal message never gets a chance to
run at all. Instead, the *second* Start.bat instance's own binary-picking step —
```
for /f "usebackq delims=" %%F in (`powershell -NoProfile -Command "Get-ChildItem -LiteralPath '.' -File | Where-Object {...} | ... -ExpandProperty Name"`) do set "TARGET=%%F"
...
"!TARGET!"
```
— fails immediately with cmd's own generic `9009` ("not recognized as an internal or
external command"), meaning `TARGET` came back empty and `"!TARGET!"` tried to execute
nothing. Start.bat then does exactly what it's designed to do for *any* crash: retries
with backoff (2s, 4s, 6s, 8s, 10s), each attempt failing the same way, prints "Panel
crashed, exit 9009, relaunch attempt N of 5" each time, and after ~43 seconds gives up
with "Gave up after 6 rapid crashes, last exit code 9009" and a `pause`.

**A non-technical operator's actual experience:** a second, brand-new console window pops
up (title "Zomboid Control Panel" — indistinguishable from the first one, which is still
fine and still running underneath). It fills with six red-looking crash messages over
about 40 seconds, then a generic "gave up" message and a "Press any key to continue"
prompt. Nothing here says "already running" or "you have two copies open" — it reads
exactly like the app is broken.

**HOW I KNOW — reproduced twice, cleanly isolated from the port-collision issue above:**
Same folder, same exe, same panel already alive and fully healthy on its own (confirmed:
the first instance stayed up, responding, still listening throughout). Solo launches (no
other instance of *that install* running) succeeded cleanly, twice. The moment a second
launch targeted a folder whose first instance was still active, it hit this 9009 loop —
100% reproducible both times I tried it, using two different real-double-click mechanisms
(Explorer UI Automation `Invoke` and `Shell.Application.InvokeVerb("open")`, i.e. not an
artifact of one particular scripting method — see Methodology notes below on why I stopped
trusting a single method).

**WHAT I DIDN'T NAIL DOWN:** the exact mechanism inside the nested `for /f` +
backtick + `powershell -NoProfile -Command` capture that makes it return empty
specifically when a second supervisor console starts while a first is already active in
the same folder. My best-supported lead, not a proven cause: some kind of contention in
that nested synchronous-pipe-capture step when two cmd.exe/powershell trees are doing it
in the same directory close together in time. This needs someone to actually instrument
Start.bat (or reproduce it manually outside of a `for /f` capture) to pin down — I did not
attempt a fix, per the brief.

**SEVERITY: High.** This is the exact failure mode god was checking for, just via a
different route than the pidLock feature — the lock is fine, but it never gets invoked
because something upstream of it breaks first, and what the operator sees is indistinguishable
from "the panel is broken," not "you already have one open."

## Finding 3 — confirmed working, worth stating so nobody "fixes" it blind

- **exe → Start.bat auto-handoff** (`server/index.js:75-109`, the "double-click the .exe
  directly and it re-launches itself via Start.bat" convenience path): works, on a clean
  solo launch. Confirmed via a genuine Explorer double-click producing a live, listening,
  fully-responsive panel.
- **Port-fallback-when-3001-taken**: works correctly at the panel level (see Finding 1) —
  it's specifically Start.bat's own banner text that's wrong, not the underlying fallback
  logic.
- **Console survives a killed parent**: force-killing the Start.bat/cmd.exe process that
  supervises the panel did **not** kill the actual panel child — it kept running,
  responding, still listening. The panel isn't fragile-tied to its supervisor console's
  process lifetime. (Caveat below — I could not test the literal "click the X button"
  signal path, only a forced parent kill, which is a different code path than a real
  window close. If a real close behaves the same way, the operator is left with an
  invisible-but-running server they'd need Task Manager to find — not tested to
  confirmation either way.)

## Finding 4 — real, but an OS-level fact of life, not a panel bug: SmartScreen blocks the exe outright when it carries Mark-of-the-Web

**WHAT I DID:** tagged a copy of the exe with a Zone.Identifier (`ZoneId=3` +
referrer/host URL), replicating exactly what Windows Explorer stamps onto a file after a
browser download and a built-in "Extract All" — i.e., the realistic state for someone who
followed the README's own instructions (download the release zip from GitHub, extract,
double-click).

**WHAT HAPPENED:** a real double-click never produced a `ZomboidControlPanel.exe` process
at all (confirmed via `Win32_Process` — zero matches, the whole time), never wrote a single
log line or data file, and spawned a genuine `smartscreen.exe -Embedding` helper that sat
pending. This is Microsoft Defender SmartScreen's "Windows protected your PC" block for an
unrecognized/unsigned binary, and it renders on an isolated secure desktop — I could not
screenshot it, could not enumerate it via UI Automation, and deliberately did not attempt
to script past it (that's a real OS security boundary, not something I should be defeating
programmatically). A real operator would need to know to click "More info" then "Run
anyway" — well-documented standard Windows behavior, but a well-known point where
non-technical users give up, thinking the download is broken or blocked "for a reason."

**NOT A CODE BUG** — the only real mitigation is code-signing the binary, which is a cost/
process decision, not something in this repo to fix. Flagging for awareness since nobody
had confirmed it fires for this specific exe before.

**NOT CONFIRMED THIS SESSION:** the Windows Firewall "allow this app on public/private
networks" prompt specifically for this exe. I initially misread an already-open, unrelated
firewall dialog (for `Node.js JavaScript Runtime`, i.e. someone's `nodemon`/dev-server
session, not my exe — caught and corrected before trusting it, see Methodology below).
None of my successful launches produced a fresh, attributable firewall prompt that I could
confirm was mine within my test window. Genuinely open, not tested to either outcome.

## Methodology notes (so the next person doesn't waste an hour where I did)

- **`Start-Process -FilePath <exe>` hung indefinitely** in this shell environment on every
  attempt, tagged or not. Root cause not fully pinned down, but it did not correlate with
  SmartScreen (a second hang happened on a completely untagged file, no MOTW, no
  `smartscreen.exe` involved). Treat this as a tooling limitation of scripted
  `ShellExecute`-style launches from a non-interactive PowerShell session, not a product
  signal.
- **`[System.Diagnostics.Process]::Start()` with `UseShellExecute=$false` (raw
  `CreateProcess`) reliably reproduced the same 9009 crash-loop as a genuine second-instance
  double-click**, even on a solo, first-ever launch with no other instance running. I
  initially took this as "the primary launch path is broken" — **that conclusion was
  wrong.** The reliable, faithful way to simulate a real double-click turned out to be
  `Shell.Application` COM (`$shell.Namespace(dir).ParseName(file).InvokeVerb("open")`) or
  Explorer UI Automation `Invoke` on the file's list item — both go through the real
  ShellExecute path Explorer itself uses and don't block the calling script. Once I
  switched to those, solo launches succeeded cleanly and consistently; only genuine
  second-instance-same-folder launches reproduced 9009. **Anyone testing this exe
  programmatically should use one of those two methods, not raw `CreateProcess`, or they
  will chase the same false lead I did.**
- No browser automation was available this session (Chrome extension not connected), so
  the actual setup-wizard UI was verified only via direct HTTP (`GET /`, `GET
  /api/auth/status` → `200`, `{"needsSetup":true,...}`), not a real visual walkthrough.
  Toby's earlier from-source pass already covered the wizard's UI behavior in detail; I did
  not re-do that here.
