# Architecture Decisions

## Stack

The panel uses a Node.js and Express backend, a React, Vite, and TypeScript client, Socket.IO for real-time updates, and a lowdb JSON database. It ships as a Docker image and standalone Windows/Linux executable.

## Server Profiles

Server profiles describe a local or remote Project Zomboid installation. Legacy `isRemote` records resolve to `native` or `remote-sftp`; the server-status model also recognizes `docker-local` and `docker-managed` values so persisted profiles remain accurately labeled. Docker lifecycle control is not integrated: provider labels do not grant Docker socket access or container management.

## PanelBridge

PanelBridge is a file-based bridge between the panel and the in-game Lua mod. The panel owns command files and reads response files; Lua only creates `.txt` files because Build 42 requires that extension. Every player's game also runs each mod's `media/lua/server`, so the bridge's first statement returns unless `isServer()` is true, and the client companion runs only in a multiplayer session. The heartbeat (`status.json`) reports `startedAt`, `gameVersion` and `delivery` (`workshop`, `mod` or `loose`, plus the Workshop item id), which the Lua reads from the path of its own running file (`getFilenameOfClosure`) and cross-checks with the active mod list.

**Delivery methods.** The Lua reaches a server in one of two ways, stored per profile as `servers[].bridgeDelivery`: `"local"` (the default, also when the field is absent) or `"workshop"`. Local means the panel copies `PanelBridge.lua` into `<install>/media/lua/server/`, and players can only join with `DoLuaChecksum=false`. Workshop means the server's `.ini` lists `ZCPB` in `Mods=` and the item id in `WorkshopItems=`, and the game downloads the item at start. The item keeps the loose file's relative paths, so only one copy can run. `services/bridgeDelivery.js` owns the decision, `GET` and `POST /api/panel-bridge/delivery` (status, a `dryRun` preview, and apply with `expectedFrom` to catch a stale page), and every write that follows from it. The server computes the state; the client only maps it to copy. When the panel can't write the install folder (remote and hosted servers, Docker without a mount), the operator gets guided steps instead, and the heartbeat confirms them.

**Effective method per install folder.** Loose files live in the game folder, so the method is decided per folder, not per profile. Non-remote profiles whose install folders resolve to the same real path (`installDirKey`: `realpath`, case-folded on Windows) form a group. If any member is `workshop`, every member is treated as Workshop, and a switch records the method on the whole group. A remote profile is its own group.

**Single writer and `reconcileBridge`.** `panelBridgeInstaller.installBridge()` is the only code that writes a loose `PanelBridge.lua`, and `bridgeDelivery.js` is its only caller. `server/tests/bridgeSingleWriterGate.test.js` enforces both. It writes only the server file, from the embedded copy first. Every automatic path goes through `reconcileBridge(server, { reason })`: boot (`"boot"`), activation (`"activate"`), the before-launch hook (`"launch"`), the setup wizard and quick setup (`"setup"`), and the Install button and Auto Setup (`"manual"`). Inside a per-folder lock it re-reads the effective method, removes stale temp files, and archives the client companion and root `mod.info` older panels wrote. For Local it then installs or updates the loose file (the `panelBridgeAutoUpdate` setting gates boot, activation and launch). The exception is a server whose own `.ini` still loads the Workshop copy with the check on: there it installs nothing, moves the loose file out, and leaves the choice to the operator. For Workshop it moves loose files out and re-adds this server's two `.ini` entries. Moved files go to `<dataDir>/bridge-delivery-archive/` with a manifest, never deleted. Reconcile never throws, and a launch waits for it at most 15 seconds.

**Before-launch hook.** `lifecycleCoordinator.setBeforeLaunchHook()` is wired at boot to `reconcileBridge(server, { reason: "launch" })`, injected rather than imported so tests that mock `database/init.js` stay isolated. It runs as the second half of `prepareForLaunch()`, right after the launch-target refresh (see [Launch target](#launch-target)). `serverManager.startServer()` calls `prepareForLaunch()` after the SteamCMD guard and before both launch branches. `managedContainer.runManagedLifecycle()` calls it for start and restart, and so does the Servers page's container Start/Restart (`routes/docker.js`). That covers dashboard, scheduled, mod-update, Discord, boot auto-start and post-update starts. A start the panel doesn't perform isn't covered.

**Mods tool guard.** `routes/mods.js` wraps `writeIniWithBackup` with `protectBridgeIniEntries()`. While the active server gets PanelBridge from the Workshop, a mod-tool write that drops the bridge's `Mods=` or `WorkshopItems=` entry (remove, toggle, collection import, load-order save) gets the entry put back at its old position. The guard never adds an entry that wasn't there, and keeps reorders. The raw and structured INI editors aren't wrapped; the next panel launch restores entries removed there. `GET /api/mods/current-config` returns `bridgeManaged` so the Mods page can badge and lock the row.

**The Workshop item id ships with each release.** `services/bridgeWorkshopRelease.js` reads `pz-mod/workshop/published.json`. It takes the copy esbuild embeds in exe builds (`PANEL_BRIDGE_WORKSHOP_JSON`) first, because a binary-only update leaves the on-disk `pz-mod/` stale. Otherwise it reads the file from the working directory, next to the executable, or relative to the module; dev checkouts and both Docker images, which copy `pz-mod/`, use the file. The id is never fetched from the network: a Workshop server runs whatever Lua that item holds, so the id has to come from the same reviewed, versioned artifact as the panel. The only override is the maintainer's `PANEL_BRIDGE_WORKSHOP_ID` environment variable, which always marks the release as a preview. Without a valid id, Workshop delivery is unavailable. The file's `liveVerified` block records the maintainer's live test, and the option carries a Preview badge until both server OSes are recorded. Publishing is described in [docs/maintainers/workshop-publishing.md](docs/maintainers/workshop-publishing.md).

**Protocol and versions.** `PROTOCOL_VERSION` (`queue-v1`) changes only for a breaking wire-format change. Bridge changes must be additive: a Workshop server runs whatever version was last published, not the panel's bundled one, and keeps it until it restarts. The bridge version (`VERSION`, the header's `Version:` and `mod.info`'s `modversion`) moves only when the Lua or `mod.info` changes. `scripts/check-bridge-version.mjs` checks it against `pz-mod/bridge-version.lock.json` in CI, on tag builds and in `release.ps1`.

**Invariants.** The delivery code and its tests are built around these:
- I1: The panel adds or removes the bridge's `Mods=` and `WorkshopItems=` entries together, never one without the other.
- I2: In Workshop mode, loose bridge files leave the install folder before every panel-driven launch. During a switch they move only after the `.ini` edit has been re-read and verified.
- I3: No automatic path writes a loose `PanelBridge.lua` into a folder whose effective method is Workshop. The method is re-read inside the per-folder lock.
- I4: Switching to Local installs and verifies the loose file first, then writes each group `.ini` once, removing the entries and setting `DoLuaChecksum=false`.
- I5: `DoLuaChecksum=true` is never written automatically. The UI offers it only once the Workshop delivery is confirmed and, where the panel can see the game folder, no loose files remain. The operator's own `PUT /api/server-files/ini` writes it.
- I6: A failed apply restores every file it touched, in reverse order. The stored method changes only after every file step has succeeded.
- I7: The launch hook never throws and never holds a start longer than 15 seconds. Problems are logged and shown by `GET /api/panel-bridge/delivery`.
- I8: Workshop can't be chosen when a group member launches without Steam, the server reports a game version below 42, or the item id is unknown. Profile creation, edits and setup refuse a profile that launches without Steam in a Workshop folder.

## Launch target

What the game reads at launch comes from the server's current settings, on every start the panel performs. `lifecycleCoordinator.prepareForLaunch(server, { container })` first calls the refresher wired at boot, `routes/server.js`'s `refreshLaunchTargetForLaunch()`. It re-reads the server record by id, because the shared `ServerManager` keeps the record from boot or the last server switch and a password-only edit doesn't reload it. Then `refreshLaunchTargetBeforeStart()` writes `RCONPassword` and `RCONPort` into that server's `.ini` and, for a managed install, regenerates `StartServer_<name>.bat` and `start-server_<name>.sh`, which carry `-servername`, `-cachedir`, `-adminpassword`, the port and memory. A container launch (`container: true`) gets the `.ini` only, before `docker start` or `docker restart`, because the image owns the launch command. No caller refreshes on its own; the boot auto-start once had no refresh at all (GH #167).

When the panel launches a managed server with a name, it launches that server's own generated script. The scripts are written into the launch folder, `serverPath || installPath`, the folder `loadConfig()` spawns in. `loadConfig()` names the script without checking the disk. `startServer()` checks right before the spawn, and before `systemctl` or `rc-service` starts a systemd/OpenRC server; `restartServer()` checks before a service restart. If it's still missing, the start fails with `SERVER_START_SCRIPT_MISSING`. The scheduler's `performRestart()` asks first, with `assertNamedStartupScriptLaunchable()` before its countdown, save and quit: when the script is missing and a test write into the launch folder fails, the restart is called off with `SERVER_RESTART_SCRIPT_MISSING` and the server keeps running. If the refresh couldn't overwrite an older copy, the start runs that copy, and the refresh logs a warning that it may carry older settings. The panel never falls back to the stock `StartServer64.bat` or `start-server.sh`: they pass no `-servername` or `-cachedir`, so the game would open the default `servertest` world and, with no admin account there, stop at a console prompt for a new admin password. A custom launcher (a stored path ending in `.bat`, `.sh` or `.exe`, see `resolveLaunchMode()`) and a custom start command run as they are.

A systemd/OpenRC unit runs the launcher baked into it when its template was downloaded (`linuxServiceLifecycle.js`'s `resolveLaunchTarget()`). For a folder install the template always names `start-server_<name>.sh`. Before GH #167 it named `start-server.sh` when the named script didn't exist yet, and a unit installed from such a template keeps running it until the operator downloads and installs the template again. A Docker-managed container runs the image's own command: the panel writes only its `.ini`, so an admin-password change doesn't reach it through a script.

## Mount Discovery

`mountDiscovery.js` probes configured and common local PZ paths for install and save-data signatures. Discovery records are trusted only on the server: the client can request a mount scan, but server creation accepts only an exact server-side discovery. `PZ_SERVER_PATH` and `PZ_SAVE_PATH` provide fallback paths when persisted fields are empty.

## Templates

Templates are sparse JSON overrides for existing `server.ini` and SandboxVars settings. Secret, identity, and networking keys are excluded. Template mutations require an administrator and applying to the active server requires a verified stopped state. Server names are validated before paths are built; writes are serialized, backed up by default, and rolled back if the second file cannot be written. Unknown INI keys are skipped rather than appended.

## Status Model

The active-server status endpoint reports three distinct signals: host/process or container state, RCON connectivity, and PanelBridge state. Healthy signals remain neutral in the client. Remote SFTP hosts are deliberately shown as unknown when the panel cannot verify their process state. A confirmed host answer (a completed native process scan, a managed systemd/OpenRC unit's settled state, or a resolved Docker container) is authoritative; a unit that is still stopping or in a state the panel cannot read counts as unknown, not stopped. When the confirmed answer is stopped, the status watchdog's verdict is stopped and the exited server's last PanelBridge heartbeat is expired at once, because the bridge's own liveness is only the age of the mod's last status-file write, which outlives the process (by up to five minutes on an empty server). The composed status also reports PanelBridge offline beside a stopped host once that write is older than the normal freshness window, but keeps a mod that wrote seconds ago active. The expired write stays expired until the mod writes again, which a restarted server only does once its world has loaded; while the server is observed running before that, the bridge diagnostics say how long the mod has been silent since the start instead of calling the server stopped.

Server uptime is computed in the client from the host signal's `startedAt`, which is present only for a host confirmed running whose start time the panel can state. For a native server that is the tracked process's OS start time (from the same `Win32_Process` row the Windows scan found it in, or from `/proc` on Linux, where a systemd-managed server is tracked by its unit's `MainPID` and an OpenRC-managed one by the child PID supervise-daemon records in `$XDG_RUNTIME_DIR/openrc/options/<service>/child_pid`), otherwise the panel's own launch-time record, which belongs to the first PID seen after that launch; a start time is never carried over to a different PID, and none is reported while no PID is known. For Docker providers it is the container's `State.StartedAt`, which is the container's start rather than the game server's if PZ is relaunched inside a running container. Remote SFTP hosts, processes the panel cannot see, and managed services between a crash and the respawn have no start time and render as unknown, never as zero. Status payloads carry `serverTime` (the host clock when it answered) so the client re-expresses `startedAt` in its own clock before counting; that leaves each response's latency in the value, so the client treats reports less than 2 seconds apart as the same start and keeps the earlier one.

## Storage Health

`diskMonitor.js` checks free space on the save volume every 60 seconds. Warning and critical thresholds are 90% and 95%. The system health endpoint combines disk state with the lowdb write circuit-breaker state; the client renders this only when a fault is present.

## File Writes

Configuration and bridge installation writes use atomic temp-file replacement. `withFileLock()` serializes concurrent writes to the same path. Multi-file operations must either complete or restore earlier files from their original content.

## Authentication

Authentication uses bcrypt password hashing, JWT access tokens, refresh cookies, timing-safe comparisons, recovery codes, and role middleware. Privileged routes use `requireRole("admin")`; the client should hide mutation controls from authenticated non-admin users while the server remains the enforcement boundary.

## Deferred Work

Docker capability discovery, managed-container metrics, and one-container lifecycle actions are disabled unless `PANEL_DOCKER_CONTROL_ENABLED=true` and the Docker socket is mounted. Even then, the panel recognizes only containers carrying `zomboid-panel.managed=true`; image names and provider labels never grant access. Lifecycle actions are administrator-only, strict-rate-limited, and re-check the label through Docker inspection immediately before acting. Resource snapshots are non-streaming and bounded to three concurrent Docker API calls. Do not infer that a Docker provider label or a detected mount permits lifecycle operations.
